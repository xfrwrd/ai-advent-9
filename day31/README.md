# Day 31 — ассистент разработчика

`/help` отвечает по документации проекта и по текущему состоянию Git. Модель не является источником истины: документы приходят из локального индекса, ветка — из MCP-инструмента.

```text
/help вопрос
    ↓
маршрутизатор day31/route.py
    ↓                         ↓
индекс документации           MCP git_current_branch
day31/index/docs.sqlite       day31/mcp_server.py
    ↓                         ↓
LocalLLMClient, think=false, qwen3:8b
    ↓
ответ + реальные источники + JSON инструмента
```

Поиск — `day22/retrieve.py` поверх `LocalHashEmbedder` из Day 21. Попадание засчитывается, только если вопрос и фрагмент делят слово или общие первые 5 букв длинного слова («запустить» и «запуск»). Если в вопросе назван `day28`, файл из этой папки поднимается выше. Одного косинуса hash-вектора недостаточно. Если совпадений нет, модель не вызывается и ответ фиксированный: «Не знаю: в документации проекта нет ответа на этот вопрос.»

Обработчик `day31/help.py` не вызывает Git. Вызов `subprocess` есть только в MCP-сервере.

## Откуда берутся документы

В индекс входят:

- корневой `README.md`;
- `docs/**/*.md` и описания API в `docs` (`.yaml`, `.yml`, `.json`);
- `day*/README.md`, кроме `day31/README.md`: в нём перечислены учебные вопросы, и индексация сделала бы ложное «совпадение» на каждый из них;
- `openapi.yaml` или `openapi.json` в корне, если файл есть.

Файла OpenAPI в репозитории нет. Исходные `.py` в этот индекс не входят. Индекс Day 21 для кода остаётся на месте и здесь не пересобирается.

Не индексируются `.env`, каталоги `.git`, `.venv`, `__pycache__`, ключи `*.pem`, `*.key` и `id_rsa`.

У каждого chunk сохраняются относительный путь, заголовок раздела, `chunk_id` и диапазон строк. Диапазон посчитан по переводам строк, это не токенизатор модели.

## Переиндексация

```bash
cd ~/Projects/ai-advent-9
.venv/bin/python -m day31.index_docs
```

Команда заново записывает `day31/index/docs.sqlite`. Файл перед записью удаляется, а одинаковый `chunk_id` второй раз не вставляется. Повторный запуск не копит копии. Каталог индекса в `.gitignore`.

## MCP tools

Сервер `day31/mcp_server.py`, транспорт stdio. Корень репозитория — `DAY31_REPO` или корень проекта. Путь снаружи в инструмент не передаётся.

| Инструмент | Что читает |
| --- | --- |
| `git_current_branch` | текущая ветка; при detached HEAD — commit и `branch: null` |
| `git_status` | `git status --porcelain`, не больше 40 строк |
| `git_diff_summary` | `git diff --stat` и staged stat |
| `list_project_files` | `git ls-files`, не больше 80 путей |

Push, reset, checkout, удаление файлов и произвольный shell не реализованы. Если директория не Git-репозиторий, инструмент возвращает `not_a_git_repo`.


Последний вопрос в документации не описан. Ожидается отказ, без вызова модели.

На странице под ответом видны документы, JSON MCP и предупреждения. У вопроса про ветку блок MCP содержит `git_current_branch`. У вопроса про RAG написано «MCP не вызывался».

## Как проверить, что ветка пришла из MCP

1. Задать `/help Какая текущая Git-ветка?`.
2. В блоке MCP увидеть инструмент `git_current_branch` и поле `branch`.
3. Сверить имя с `git rev-parse --abbrev-ref HEAD` в другом терминале.
4. В `day31/help.py` нет `subprocess` и `rev-parse`. Их вызывает только MCP-сервер.

## Ограничения

- Индекс не содержит исходный код, только README, docs и найденные схемы.
- Совпадение по первым пяти буквам не заменяет нормальный поиск по смыслу. Совсем другая формулировка по-прежнему может не найти фрагмент.
- История `/help` на странице живёт до обновления вкладки и в индекс не пишется.
- Ответ модели может сформулировать мысль своими словами. Список файлов на экране построен из найденных chunk, а не из текста модели.
- Живой прогон через Qwen в этот README не записан, пока он действительно не выполнен.
