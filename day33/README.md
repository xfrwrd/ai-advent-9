# Day 33 — ассистент поддержки DemoPortal

Учебный сервис с входом в личный кабинет. Ассистент соединяет два разных источника:

- RAG — общие инструкции: как устроен вход, что значит код ошибки, когда звать оператора;
- MCP — данные конкретного обращения: чей тикет, какой код, какой статус.

Модель не является источником истины. Чужой тикет не попадает в промпт.

```text
вопрос
    ↓
demo-пользователь и режим (не текст вопроса)
    ↓
MCP: get_user, list_user_tickets, затем get_ticket и get_ticket_history
    ↓
индекс day33/index/support.sqlite
    ↓
LocalLLMClient, think=false, qwen3:8b
    ↓
ответ + источники + JSON инструментов
```

Поиск переиспользует `day31/retrieve.py` и `LocalHashEmbedder` из Day 21. Попадание засчитывается, только если вопрос и фрагмент делят слово. К запросу добавляются код ошибки и краткое описание тикета, поэтому фраза «не могу войти» не выбирает причину сама: её задаёт тикет. Если совпадений в базе знаний нет, модель не вызывается.

`day33/support.py` не читает `support.json` и не вызывает Git. JSON читает только `day33/mcp_server.py`.

## Файлы

- `day33/knowledge/` — FAQ, вход, восстановление доступа, коды ошибок, эскалация;
- `day33/data/support.json` — 3 пользователя и 5 тикетов, синтетические;
- `day33/mcp_server.py` — read-only MCP;
- `day33/mcp_client.py` — stdio-клиент;
- `day33/index_support.py` — сборка индекса;
- `day33/support.py` — проверка доступа, RAG, промпт, ответ;
- `day33/sessions.py` — история диалога;
- `day33/ui.py` — страница Streamlit;
- `day33/check_support.py` — живой прогон с Qwen, не входит в unittest.

## MCP

Сервер `day33/mcp_server.py`, транспорт stdio. Файл данных — `DAY33_DATA` или `day33/data/support.json`.

| Инструмент | Что читает |
| --- | --- |
| `get_ticket` | один тикет; неизвестный id → `not_found` |
| `get_user` | имя, статус учётки, маска контакта |
| `list_user_tickets` | тикеты этого пользователя, без текста сообщений |
| `get_ticket_history` | сообщения одного тикета |

Инструментов записи нет. Поле `password`, если его добавить в JSON, в ответ `get_user` не попадает.

Инструмент сам не знает, кто вошёл в страницу. Граница доступа — `support.answer`: в режиме пользователя он сначала вызывает `list_user_tickets` и только потом `get_ticket`. Чужой id отклоняется до модели.

## RAG

В индекс входят только `day33/knowledge/*.md`. JSON с людьми и тикетами не индексируется. У chunk сохраняются путь, раздел, `chunk_id` и смещения в файле.

Повторная индексация удаляет `day33/index/support.sqlite` и пишет его заново. Одинаковый `chunk_id` второй раз не вставляется.

```bash
cd ~/Projects/ai-advent-9
.venv/bin/python -m day33.index_support
```

Это не индекс Day 31 и не индекс Day 32.

## Доступ

Личность в учебном проекте — выбранный в интерфейсе demo-пользователь, а не `user_id` из текста вопроса. Фраза «я demo-user-2» не переключает актора.

Режим `user` видит только свои тикеты. Режим `operator` включается отдельным переключателем и может прочитать любой тикет. Из текста вопроса режим не меняется.

Сессия хранит не больше 8 сообщений и 2000 символов. Если тот же `session_id` открыть другим пользователем или в другом режиме, история не отдаётся.

## Запуск

```bash
cd ~/Projects/ai-advent-9
.venv/bin/python -m day33.index_support
.venv/bin/streamlit run day33/ui.py
```

Один вопрос из терминала. Этот вызов обращается к живой модели:

```bash
.venv/bin/python -m day33 --user demo-user-1 --ticket ticket-101 "Почему я не могу войти?"
```

Ollama должна слушать `127.0.0.1:11434`, модель `qwen3:8b`. В облако вопрос не отправляется.

## Сценарии

1. Пользователь Анна Демо (`demo-user-1`), тикет `ticket-101` с кодом `ACCOUNT_LOCKED`. Вопрос: «Почему я не могу войти?». Ответ опирается на статус тикета и инструкцию «подождать 30 минут», с источниками FAQ.
2. Следующий вопрос в той же сессии: «А что делать дальше?». В промпт входит предыдущая реплика и тот же тикет.
3. Тем же пользователем нажать «Запросить чужой тикет ticket-103» (он у Бориса Демо). Тот же отказ даёт поле «Проверка доступа», если вписать `ticket-103` и нажать «Спросить». Отказ приходит до модели, `get_ticket` не вызывается.

Живой прогон всех трёх сценариев:

```bash
.venv/bin/python -m day33.check_support
```

## Ограничения

- Нет настоящей учётной записи: demo-пользователь выбирается в интерфейсе.
- MCP-инструмент, вызванный напрямую, читает любой id. Ограничение стоит в `support.answer` и на странице.
- Данные в памяти процесса. Перезапуск страницы очищает историю.
- Операторский режим не защищён паролем. Это отдельный переключатель для демонстрации.
- CRM, PostgreSQL, Docker и облачная модель не используются.

## Проверено

18 тестов `python -m unittest discover -s day33` проходят с mock-моделью. Реальный MCP-сервер в этих тестах вызывается для чтения тикета, пользователя, списка, отсутствующего id и отказа в чужом тикете.

`python -m day33.check_support` с живой `qwen3:8b` прошёл: по `ticket-101` ответ про блокировку на 30 минут и источники FAQ, продолжение диалога осталось на том же тикете, `ticket-103` отклонён до `get_ticket` и до модели. Та же страница проверена в браузере на `http://127.0.0.1:8533`.
