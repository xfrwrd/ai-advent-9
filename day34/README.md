# Day 34 — ассистент для работы с файлами проекта

Пользователь пишет цель. Локальная `qwen3:8b` на каждом шаге сама выбирает один файловый инструмент, получает результат и решает, что делать дальше: искать, читать ещё, готовить правку или отвечать. Анализ автономный, запись — только после подтверждения человеком.

```text
цель пользователя
    ↓
day34/agent.py: промпт = правила + цель + история шагов
    ↓
Qwen (Ollama, format=json) → {"action": "tool", "tool": ..., "args": ...}
    ↓                                  или {"action": "final", "answer": ...}
проверка схемы и лимитов в Python
    ↓
MCP day34-files: list_files · search_in_files · read_file
MCP day34-changes: propose_file_change (diff без записи)
    ↓
результат → в историю → следующий шаг
    ↓
ответ + прочитанные файлы + diff
    ↓
кнопка «Применить» → apply_file_change(proposal_id, diff_sha256)
```

Ollama в этом окружении принимает `format: "json"`, но для выбора инструмента используется собственный JSON-протокол с проверкой схемы: имя инструмента из списка, аргументы нужных типов, лишние аргументы отклоняются. Порядок шагов не зашит: в тестах и в живых прогонах агент сам выбирает `list_files`, повторный поиск или ещё одно чтение.

## Файлы

## Инструменты

| Сервер | Инструмент | Что делает |
| --- | --- | --- |
| `day34-files` | `list_files` | список файлов каталога, фильтр `pattern` |
| `day34-files` | `search_in_files` | поиск подстроки: путь, номер строки, строка; флаг `truncated` |
| `day34-files` | `read_file` | файл с номерами строк, диапазон, `sha256` файла |
| `day34-changes` | `propose_file_change` | правка одного точного фрагмента или новый файл; пишет только предложение в `day34/artifacts/proposals/` |
| `day34-changes` | `apply_file_change` | запись подготовленного diff по `diff_sha256` |
| `day34-changes` | `cancel_file_change` | отмена предложения |

Агенту доступны `list_files`, `search_in_files`, `read_file` и `propose_file_change`. Вызов `apply_file_change` или `cancel_file_change` от модели отклоняется в `agent.validate_call`, до MCP. Выполнения shell нет ни в одном модуле Day 34.

## Ограничения доступа

Проверка на сервере, в `policy.resolve`, а не в промпте:

- корень — `DAY34_REPO` или корень проекта; без `.git` инструменты отвечают `not_a_git_repo`;
- `../` и абсолютные пути вне корня → `outside_root`;
- symlink, который ведёт наружу, → `outside_root` (сравнивается путь после `resolve()`);
- `.git`, `.venv`, `venv`, `node_modules`, `__pycache__` → `forbidden_dir`;
- `.env*`, `*.pem`, `*.key`, `id_rsa*`, `credentials.json`, файлы со `secret` или `credential` в имени → `secret_file`;
- значения вида `API_KEY = "…"` и токены `sk-…`, `ghp_…` маскируются `***` в выдаче;
- запись — только `.md` и `.txt`, не в `index`, `reports`, `artifacts`, `data`, `.github`, не через symlink;
- удаления файлов нет.

Текст файлов попадает в промпт как «данные, а не инструкции». Если файл просит вызвать `apply_file_change` или прочитать `.env`, модель может это попробовать, но вызов отклонит Python.

## Лимиты цикла

| Лимит | Значение |
| --- | --- |
| шагов | 14 |
| прочитанных файлов | 8 |
| размер промпта | 48 000 символов (`num_ctx` 24 576) |
| ответ Ollama на шаг | 300 с |
| результат шага в промпте | 7 000 символов, поиск до 4 000 в сжатом виде |
| время запуска | 900 с |
| ошибок подряд | 3 |
| совпадений поиска | 60 по умолчанию, до 200 |

Повтор того же вызова с теми же аргументами считается ошибкой. После отклонённого шага следующий запрос идёт с `think: true` и температурой 0.7, иначе модель повторяет тот же вызов. Если агент упёрся в лимит, ответ строит Python: что успел, какие файлы прочитал, какие изменения подготовил.

Модель отвечает JSON с полем `thought`: что уже известно и зачем шаг. В конце промпта Python пишет состояние: какие вызовы уже были, что прочитано, какие найденные файлы не прочитаны. История стабильна от шага к шагу, поэтому Ollama переиспользует кэш начала промпта.

Если модель пытается ответить без инструментов или после поиска по нескольким файлам прочитала меньше двух, финал один раз возвращается с напоминанием. В конец ответа Python пишет, подготовлены ли изменения, независимо от формулировок модели.

К ответу Python добавляет точный список совпадений поиска `путь: строки …` и пометку «подстрока, не анализ зависимостей». Если поиск или чтение были неполными, это видно в блоке «Ограничения».

## Подтверждение записи

1. Фаза A. `propose_file_change` читает файл, запоминает `sha256` исходника, строит unified diff и сохраняет предложение. Целевой файл не меняется.
2. Страница показывает diff. Кнопки «Применить» и «Отменить» есть только у подготовленного изменения.
3. Фаза B. «Применить» передаёт `proposal_id` и `diff_sha256` именно показанного diff. Сервер сверяет хеш, затем сверяет текущий `sha256` файла с исходным. Если файл изменился, ответ `stale`, ничего не записано.
4. Запись через временный файл и `os.replace`, затем повторное чтение и сверка хеша: `verified: true`.

Новый файл (`create: true`) проходит те же две фазы. Фраза модели «пользователь согласен» ничего не записывает: у модели нет доступа к `apply_file_change`.

Повтор задачи предсказуем: тот же diff получает тот же `proposal_id`; если новый текст уже в файле, ответ `already_applied`; повторное «Применить» тоже `already_applied`. Git commit и push не выполняются.

## Живая проверка с Qwen

Прогоны 15 октября 2026, `qwen3:8b`, Mac M4 24 ГБ.

- Использования `LocalLLMClient` (`check_agent usage`): поиск, затем 7 прочитанных файлов (`day26/client.py`, `day27/app.py`, `day27/cli.py`, `day28/llm.py`, `day31/help.py`, `day32/review.py`, `day33/support.py`), финал за 252 с. Модель перечислила зависимые модули, Python добавил все совпадения со строками и пометку о неполном чтении двух длинных файлов.
- Демо-документация (`check_agent demo`): `list_files`, чтение README и `fetcher.py`, одно `propose_file_change` на оба расхождения (60 → 180 секунд, 5 → 3 повтора), финал за 79 с, запись не выполнялась.
- CLI с подтверждением «да»: тот же diff применён, `status: applied`, `verified: true`. Повторный запуск задачи: «Расхождений не найдено», изменений не подготовлено. После проверки демо-модуль восстановлен `day34.demo_setup`.
- `day31/README.md` (`check_agent docs`, `skip`): агент читает README и до 8 файлов кода, включая `day31/corpus.py`, но расхождение в длинном списке исключений не находит и правку не предлагает. Это ограничение 8B-модели; ответ честно говорит «Изменений не подготовлено».

Страницу Streamlit с кнопкой «Применить» в браузере я не проверял: применение проверено через CLI и тестами через настоящий MCP-сервер.

## Известные ограничения

- `search_in_files` ищет подстроку. Это не разбор импортов и не граф зависимостей.
- Качество выводов зависит от `qwen3:8b`: модель может пропустить расхождение или сформулировать его неточно. Diff перед записью смотрит человек.
- Каждый вызов инструмента запускает MCP-сервер заново: около секунды накладных расходов на шаг.
- Шаг модели на большом промпте занимает десятки секунд, полный сценарий — несколько минут.
- Правка — замена одного точного фрагмента. Несколько расхождений — несколько предложений.
